"Deploy concluído com sucesso" não é o mesmo fato que "está no ar no domínio do cliente" — existe uma etapa de promoção/alias que este projeto nunca verificou explicitamente até hoje. Não é bug no código do MFA; é a lacuna de processo que o protocolo propõe fechar. Sem acesso de API à Vercel neste ambiente (conector MCP devolveu 403 Forbidden — token sem escopo pro time connectioncyberso), a confirmação final depende de checagem manual no painel da Vercel pelo usuário.

2.1 Decisão de calibragem — onde o fluxo Commit→PR→Merge→Backup→Deploy se aplica

Lido literalmente, o protocolo pediria Pull Request e revisão pra toda alteração — inclusive dentro do próprio ambiente de desenvolvimento. Isso contradiria a premissa 1 do próprio protocolo (staging = "ambiente exclusivo de desenvolvimento") e não reflete como este projeto opera (desenvolvimento solo, sem segundo revisor por commit). Leitura adotada, registrada aqui pra não ser reinterpretada silenciosamente depois:

Dentro de staging: commit → push direto, sempre precedido de teste local + tsc --noEmit limpos.

Na promoção staging → main: fluxo completo do protocolo — PR, revisão, backup de produção antes de qualquer merge, só então deploy. Não muda a prática atual porque este projeto nunca promoveu nada a produção ainda; o protocolo só torna o checklist concreto em vez de implícito.

Nova seção "Protocolo Staging-First (versionamento e deploy)" adicionada, cobrindo: tsc --noEmit obrigatório antes de commit, aviso antes de comando outward-facing, e o checklist do M-Gate Versionamento abaixo. O arquivo continua sendo a regra persistente consultada no início de toda sessão.

4. M-Gate Versionamento — checklist obrigatório

  • Staging atualizado (working copy corresponde ao que será testado/commitado).
  • Testes locais aprovados (npm test do(s) app(s)/pacote(s) afetado(s)).
  • Tipos validados (npx tsc --noEmit ou npm run type-check limpo).
  • (Só na promoção a produção) PR revisado.
  • (Só na promoção a produção) Backup de produção realizado.
  • Deploy autorizado — e confirmado como promovido ao domínio real, não só "build concluído".
  • Monitoramento pós-deploy contínuo — reconferir o comportamento real na URL pública, não só o status do CI/Vercel.
