Publicar o portal

bloqueia tudo abaixo

Sem isso nenhum usuário real — dono da Mania de Modas ou equipe — consegue abrir o sistema fora do computador de quem desenvolve.

  1. Criar o projeto Vercel do apps/portal — feito

    Projeto connectioncyber-portal criado via CLI (conta connectioncyberso, mesma da configuração anterior de domínio), conectado ao repositório connection-cyber-so/connectioncyber, Root Directory apps/portal, Framework Preset Next.js (precisou correção manual — ficava nulo por padrão ao criar via CLI, mesmo bug que já aconteceu com apps/site).

  2. Variáveis de ambiente — feito

    Mesma convenção de apps/site/apps/platform: staging (ozvylnaipubrmaadikvk), nunca produção. Configuradas em Production, Preview e Development.

    NEXT_PUBLIC_SUPABASE_URL=https://ozvylnaipubrmaadikvk.supabase.co
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=<chave publishable de staging>
PORTAL_CENTRAL_HOSTS=portal.connectioncyber.com.br

    Pendência menor: a Vercel não deixou trocar a Production Branch de main pra staging pela API — só pelo painel (Settings → Git → Production Branch). O deploy de produção atual já foi feito direto do código local via CLI (contorna essa configuração por enquanto), mas um push futuro em main vai gerar um novo deploy de produção e sobrescrever este — trocar esse dropdown evita a surpresa.

  3. Anexar os domínios — curinga, feito do lado da Vercel

    portal.connectioncyber.com.br e *.connectioncyber.com.br já estão anexados ao projeto connectioncyber-portal e verificados (confirmado por API). Existem 13 outras empresas na fila além da Mania de Modas (lista em DadosConnectionCyber/dominio connectioncyber.txt) — resolver isso uma vez com curinga evita repetir este passo pra cada uma.

    Único passo que falta — só você faz, é a Hostinger:

    Tipo: CNAME
Nome: *
Aponta para: cname.vercel-dns.com

    Mesma tela onde o registro www já foi configurado antes. Não mexe em mais nada — MX, SPF, DMARC do e-mail continuam intocados. Depois de salvar, a propagação costuma levar de minutos a poucas horas; o certificado SSL sai sozinho assim que propagar.

    O curinga só resolve a camada de rede. Cada uma das outras 13 empresas continua precisando do próprio ciclo completo (tenant provisionado, linha em erp_tenant_domains, dono convidado) antes do subdomínio dela responder com algo — isso fica de fora deste manual, focado na Mania de Modas.

  4. Registrar o domínio da empresa no banco — feito

    Sem esta linha, maniademoda.connectioncyber.com.br resolvia SSL/DNS certo mas o app devolvia 404 de propósito (tenant não mapeado) — foi exatamente o que aconteceu até esta linha ser inserida.

    CampoValor
    hostnamemaniademoda.connectioncyber.com.br
    domain_typesubdomain
    statusactive
    is_primarytrue
    verification_methoddns_cname

  5. Não construir roteamento novo

    Uma proposta circulou sugerindo middleware.ts reescrevendo cada subdomínio pra uma rota /loja/[tenant]. Não é necessário e não deve ser feito — o apps/portal já resolve tenant por subdomínio via classifyPortalHostname + RPC portal_resolve_host, com isolamento por RLS e membership real. Um rewrite genérico duplicaria isso com um padrão mais fraco, sem RLS. O DNS curinga (passo anterior) já basta.

  6. Provar que está de pé — confirmado

    https://maniademoda.connectioncyber.com.br/login responde 200 e mostra "Entrar em Mania de Modas" — SSL válido, tenant reconhecido pelo nome, sem sessão nenhuma. Critério de aceite do portão cumprido.

1

Ativar o dono(a) real — fecha o M18-G22

precisa da pessoa

Nenhum destes passos eu faço sozinho — é sempre a pessoa real na outra ponta.

  1. Confirmar que o convite chegou

    Já foi enviado em 01/09. Se não estiver na caixa de entrada, checar spam antes de reenviar. Reenvio é pelo Supabase Studio (staging) → Authentication → Users → localizar o e-mail → Resend invitation. Não reenviar pelo script de provisionamento — ele foi feito pra criar, não repetir.

  2. A pessoa aceita e cria a senha

    Clica no link do e-mail, define senha própria. Ninguém da equipe vê ou escolhe essa senha.

  3. Cadastro obrigatório de MFA

    O papel owner exige MFA (AAL2) — sem isso a sessão não abre o portal de verdade. App autenticador (Google Authenticator, Authy, ou o que a pessoa já usar).

  4. Primeiro login de verdade

    Em https://maniademoda.connectioncyber.com.br/login (Portão 0 tem que estar de pé). Entra, vê o próprio dashboard, nada de outro tenant. Esse é o instante em que a Mania de Modas deixa de trabalhar às cegas.

2

Criar os demais usuários reais

precisa de dados seus

Autorização registrada — mas eu não invento nome nem e-mail de ninguém. Preciso do dado real de cada pessoa antes de criar a conta dela.

Pra cada pessoa nova (vendedor, caixa, gerente): nome completo, e-mail real que a pessoa usa de verdade, e o papel dela (owner/admin/uma função operacional futura). Sem isso não tem quem convidar.

  1. Coleta protegida

    Mesmo mecanismo do dono — cofre local (DPAPI), nunca em texto solto no chat, e-mail ou planilha comum. Cada nova pessoa é um convite via Authentication → Invite user no Studio de staging, com o papel certo já escolhido.

  2. Papel define o que a pessoa vê

    owner/admin enxergam tudo do tenant; um papel operacional (caixa, vendedor) vê só o necessário — a RLS decide, não a tela. Se a Mania de Modas só tem o dono(a) usando por enquanto, este portão fica em espera até surgir a segunda pessoa real.

  3. Cada novo convite repete o Portão 1

    Aceite + MFA + primeiro login — sem atalho, mesmo pra quem já é conhecido da equipe.
