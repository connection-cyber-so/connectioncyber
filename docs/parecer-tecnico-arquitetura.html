02

A pergunta que decide tudo o resto

Você perguntou: "um Supabase e uma Vercel, ou um projeto por cliente?" — essa resposta determina a estrutura de pastas, a estrutura de repositórios e como uma rotina fiscal nova chega a todos os clientes. As três opções reais:

OpçãoComo funcionaRotina fiscal nova em todos os clientesIsolamento de dados
recomendada
A — Plataforma única
1 Supabase, 1 Vercel		 Uma tabela tenants + tenant_id em cada tabela de negócio. RLS separa os dados de cada cliente dentro do mesmo banco. 1 deploy — a mudança entra no código da plataforma e vale para todos os clientes na hora. Lógico (RLS). Forte na prática; depende de política bem escrita.
B — Um projeto por cliente
N Supabase, N Vercel		 Cada cliente tem seu próprio projeto Supabase, seu deploy Vercel, seu domínio, seu repositório. N deploys — a mesma migration/rotina precisa ser aplicada manualmente em cada projeto. Físico, total. Cada cliente numa instância Postgres separada.
C — Schema por cliente
1 Supabase, N schemas		 Um projeto Supabase só, mas cada cliente vive num schema Postgres separado (maniademodas.clientes em vez de public.clientes). Meio-termo — a migration ainda roda N vezes (uma por schema), mas dentro de 1 projeto só. Mais forte que RLS, mas exige configurar o PostgREST/Supabase para expor múltiplos schemas — atrito operacional maior do que o benefício aqui.
03

Respondendo direto: "não sei se ficou claro"

Ficou. Você quer duas coisas ao mesmo tempo, e elas não se cancelam — só exigem separar onde a separação acontece:

  • Gerenciar cada cliente separadamente → isso é uma questão de dados, resolvida pela tabela tenants + RLS. Você vê, edita e fatura cada cliente isoladamente dentro do mesmo sistema — como qualquer SaaS de mercado faz (é assim que uma única instância atende milhares de lojas em plataformas de e-commerce, por exemplo).
  • Não refazer rotina um a um → isso é uma questão de código. Rotina fiscal, cadastro de cliente/fornecedor/funcionário — tudo isso vira uma função dentro da mesma plataforma. Muda uma vez, vale para a Mania de Modas e para o próximo cliente automaticamente.

A estrutura de "uma pasta e um repositório por cliente" que você descreveu resolve a primeira necessidade, mas contradiz a segunda — é exatamente o modelo Opção B, onde toda rotina comum precisa ser copiada manualmente. Por isso a recomendação abaixo separa as duas coisas: um sistema só (rotina compartilhada), dados isolados por cliente dentro dele (gestão separada).

05

Isolamento — como um cliente nunca vê o outro

Pergunta direta, resposta direta: se fosse minha empresa, eu escolheria isolamento em camadas dentro de um projeto só — nunca um projeto por cliente apenas por causa disso. Um projeto Supabase por cliente é isolamento por força bruta (funciona, mas você paga com a duplicação de rotina que já vimos na seção 2). Camadas bem feitas isolam tão bem na prática quanto um banco físico separado, e continuam permitindo 1 atualização só.

As 6 camadas, na ordem em que uma requisição passa por elas

1. Login → JWT carrega o tenant_id do usuário (não escolhido por ele) 2. API/servidor → deriva tenant_id da sessão; nunca aceita tenant_id vindo do navegador 3. Postgres RLS → compara tenant_id do token com o da linha, antes de devolver qualquer dado 4. Storage → arquivos em tenants/<id>/..., com RLS própria (mesma lógica, outro recurso) 5. Auditoria → logs_access / remote_logs registram tentativas negadas, não só as aceitas 6. Admin (você) → cruza tenants quando precisa, mas cada uso fica registrado (break-glass)
06

Atualizar tudo de uma vez, ou por cliente?

As duas, dependendo do que está mudando — e isso é seguro sim, desde que a separação seja uma flag, não um fork:

  • Estrutura do banco (uma coluna nova, uma tabela nova) é sempre global nesta opção — não existe "aplicar só para um cliente" em nível de schema. Por isso toda migration precisa ser aditiva (nunca remove ou renomeia direto) e passa primeiro pelo branch de staging antes de tocar o banco real — é exatamente o que a seção 7, etapa 04, já prevê.
  • Regra de negócio (a rotina fiscal em si, um cadastro novo, um cálculo diferente) fica atrás de uma feature flag por tenant. Isso sim você liga cliente por cliente, no seu ritmo — inclusive testando com um cliente piloto antes de expor pros outros 14.

As "particularidades" que você listou, traduzidas para o modelo

Nenhum dos termos do seu glossário, sozinho, justifica sair da Opção A — todos viram configuração dentro da mesma plataforma:

O que você descreveuVira, no modelo recomendadoExemplo
Requisito Customizado · Demanda de Nicho · Escopo Específico Configuração por tenant (tenant_settings, campo jsonb) — não infraestrutura nova Mania de Modas cadastra grade de tamanho BR (PP–GG) em vez de numérico
Segmentação de Mercado O vertical do tenant carrega um conjunto de módulos — já reservado no schema (varejo_*, food_*) Cliente de food vê módulo de cardápio; cliente de varejo não vê
Divergência Operacional · Assimetria Operacional Módulo opcional plugável, ligado só para aquele tenant via feature flag — não é fork do núcleo Um cliente exige aprovação de compra em 3 níveis; outro em 1
Particularidade do Modelo de Negócio Tier/plano comercial — o contrato define o que fica ligado Plano "Enterprise" libera relatório fiscal avançado

O gatilho real para sair da Opção A e abrir um Supabase dedicado não é uma dessas particularidades — é exigência jurídica/contratual de isolamento físico por escrito. Até lá, tudo isso é configuração, não infraestrutura.
