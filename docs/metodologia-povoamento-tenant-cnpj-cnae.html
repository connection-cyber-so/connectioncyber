Metodologia de povoamento de tenant via CNPJ + cenário por CNAE

Trazida da auditoria de C:\Users\joaqu\Downloads\BPO — documenta o padrão, não importa os dados específicos do documento original.

O que é

  1. Consulta de CNPJ pela nossa própria Edge Function lookup-cnpj (já implantada e testada) — razão social, CNAE, porte, situação cadastral, município/UF, data de abertura.
  2. CNAE decide quais módulos fazem sentido para aquele tenant — não um pacote fixo igual pra todo mundo. Já coerente com module_catalog + tenant_modules.
  3. Separação de risco por tipo de dado: dado cadastral é registro público (risco baixo); qualquer cenário associado a um módulo, se descrever problema real de empresa real, é sensível — regra: sempre fictício-mas-realista.

Por que não importei os 10 CNPJ do documento original

As 10 empresas do parecer fonte foram povoadas no staging do bpo-system-web-os, vinculadas ao tenant "Connection Cyber Assessoria" daquele sistema — sem relação com o ConnectionCyberSO. Importar o CNPJ/nome delas aqui apresentaria empresas reais como clientes de uma plataforma com a qual não têm vínculo — exatamente o risco que o próprio documento fonte identifica.

Soma-se um problema estrutural: bpo-system-web-os tem staging e produção em projetos Supabase separados; o ConnectionCyberSO hoje tem um projeto só (qfggetvashdxyuvlhihq) — não existe onde povoar dado de demonstração sem cair "em produção".

Pronto para uso imediato

lookup-cnpj já resolve a consulta sem trabalho adicional, e tenant_modules.status = 'diagnosticado' já suporta "CNAE decide módulo" sem tabela nova — assim que houver um tenant real (ou uma separação staging/produção segura) para aplicar o padrão.

Padrões correlatos para apps/platform (ainda não iniciado)

RBAC por pilar/módulo Referência: user_module_access + get_authorized_departments() em bpo-system-web-os. Gap atual: ConnectionCyberSO só tem papel global, sem granularidade por módulo dentro do mesmo tenant.
Registro operacional genérico Núcleo comum (id, tenant_id, title, status, assigned_to, created_by, closed_at) + metadata jsonb por módulo + evento genérico campo_alterado em vez de tipo fixo por módulo. Referência: Parecer_Tecnico_Arquitetura_Comum_Pilares.docx.
